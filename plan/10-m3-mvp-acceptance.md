# 步骤 7 · M3 一期验收、部署与回退

更新日期：2026-10-30。状态：待实施，以下均为待测要求。返回 [计划目录](README.md)。前置：[09 独立推搜页面](09-m2b-recommendation-ui.md)。二期入口：[11 供应商 API](11-a0-provider-api.md)。

## 1. 一期交付边界

验收通过即完成题目推搜 MVP，可以独立部署，不等待模型接入、会话记忆、向量检索或生成式召回。部署仍使用现有应用和数据库。

产品入口为独立推搜页面；默认沿用 newfe 构建和发布，后端仍为现有 Spring Boot。协会前端复用、任务表单预填和浏览器 AC 后推荐注入均不属于本次交付。可选 E0 的资源、质量与性能结果另行记录，不混入零模型基线。

输入为各步骤代码及迁移、试点数据质量和采集演练记录、固定评测集、运行配置及必要备份。本文不是已经通过的验收报告。

## 2. 必须覆盖的端到端案例

| 类别 | 检查内容 | 通过条件 |
| --- | --- | --- |
| CF 同步 | 分页中断、重复拉取、待判题转 AC、可信重判撤销 | 无重复计数，进度可恢复，状态更正生效 |
| 洛谷上传 | 响应丢失重传、重载恢复、绑定不符、未监听历史 | 幂等、归属正确、缺口不冒充完整 |
| 清洗 | 重复提交、重复 AC、B1/B2、镜像题、同名不同题 | 来源可追溯，去重和别名准确 |
| 时间 | 秒/毫秒、跨日、时区、历史补传 | 提交与接收语义正确，不制造虚假近期新增 |
| 搜索 | 标签、难度、关键词 OR、已做题、分页 | 硬约束生效，稳定结果不漏掉后续页 |
| 推荐 | 巩固/探索、冷启动、部分覆盖、候选不足 | 采用明确条件，不编造能力结论 |
| 最终校验 | 推荐期间新 AC 入库 | 返回前重新过滤当前可读的新事实 |
| 题单和反馈 | 重试、同键不同内容、越权、换题和撤销 | 幂等，私有数据隔离，历史快照不被覆盖 |
| Hot | 多次 AC、改绑、别名、补传、现役变化 | 按规定的去重用户及历史首次观测计算 |
| 独立前端 | 通用登录、成员入口、搜索到反馈闭环、乱序响应 | 不依赖协会布局或任务表单，权限与服务端一致 |
| 原业务兼容 | 共享搜索/题号解析的旧调用方、正式任务副作用隔离 | 原契约保持，推搜不创建任务或触发奖励；无需新增任务集成 |
| 无模型运行 | 无 Key、无本地模型/运行库，Agent 与语义增强关闭 | 启动及全部一期基线功能正常，LLM/Embedding 调用均为 0 |

每项记录输入范围、预期、实际和证据。未演练的外部采集段标为未验证，不能用本地模拟或构建结果代替生产同步结论。

## 3. 搜索与推荐效果评测

准备至少 50 条结构化查询，覆盖精确题号、中英文算法同义词、平台/难度、多标签、未知细类、无匹配、已做题及分页。与原标题搜索基线比较相关性和无结果率，记录硬约束错误。

准备至少 20 组真实用户与明确训练目标，由队员或教练评价题型、难度、巩固/探索配比和理由可理解性。调参样本与验收样本分开，先建立规则基线，再约定效果阈值。

验收样本中硬约束违规目标为 0。少量样本通过不证明全部情况永无错误；真实采集覆盖不足时记录限制，不能把缺失当作未做或不会。

历史回放只使用当时可知的数据。没有历史标签、难度或热度快照时标明不能验证的部分；推荐与下一次 AC 匹配也不能独立证明训练能力提升。

## 4. 性能与运行测量

记录题库规模、原始提交行数、单用户历史量、账号数量、查询范围、并发、P50/P95、失败率、SQL 计划、数据库负载和清洗耗时。

运行环境以实际部署为准。当前用户提供的是 16 vCPU 老款 Xeon 虚拟机、约 32.9 GiB 可用内存、根分区剩余 6.0 GiB 的单次快照；部署前复查资源、容器限制、可用数据盘和现有业务负载。负载均值不能换算为空闲核心，Swap 已满也不能单独证明持续内存压力。详见 [03](03-technology-options.md)。

可将约 2,000 道候选、5 并发下结构化搜索/推荐 P95 ≤ 1 秒作为初始试点目标，再在真实完整规模下复测。此目标未实测，不代表当前系统已达到，也不能只报告候选规模而忽略原始提交规模。

先以低并发取得基线，再逐步增加负载；同时观察原有排名、提交采集和数据库查询，不能用新功能达标掩盖旧业务退化。上述目标仅针对结构化链路，不适用于尚未测量的 CPU Embedding 或供应商 LLM。

先优化字段投影、聚合、索引、分页与请求内复用。只有实测需要才增加 Redis 缓存或 user_problem_progress 汇总表，同时实现绑定、判题、标签、别名和反馈变更后的失效规则。

优先验证核心数据口径、并发幂等、权限、故障恢复及任务副作用。文档修改不触发业务运行测试；实现阶段按变更范围执行有意义的业务检查，不为简单展示和访问器堆叠测试。

## 5. 部署顺序

1. 核对部署版本、数据库备份和实际 Flyway 状态，审查兼容迁移。
2. 以新增功能关闭的配置部署兼容代码及本期迁移，保留原业务入口。
3. 用只启用清洗的配置处理试点；不启动周常派发、奖励和贡献结算调度。
4. 验证标签/别名、同步状态和关键查询，再开启独立推搜路由供少量真实队员使用；Agent 和语义增强保持关闭。
5. 执行上述端到端案例，记录实际结果、限制和性能。
6. 在试点通过后扩大范围，观察来源覆盖、错误、慢查询与用户反馈。

不在实施文档中存放生产密码、API Key 或完整个人资料。配置清洗批量、执行预算、排序版本和功能开关；一期无需模型配置。

## 6. 故障演练与回退

| 场景 | 预期行为 |
| --- | --- |
| 清洗中断 | 保留已提交有效数据与检查点，恢复后结果一致 |
| 外站采集失败 | 展示最近已知数据范围；不清空历史或标记补齐完成 |
| 账号冲突或事实查询失败 | 不承诺可靠个性化排除，返回明确状态 |
| Redis 故障 | 若已使用缓存，限流回源；不能绕过事实与反馈 |
| MySQL 故障 | 返回可重试错误，不能伪造新推荐成功 |
| 新推搜功能需回退 | 关闭入口/功能开关，保持旧接口兼容和正式协会业务 |

回退保留原始记录与新增个人快照，不通过删除源数据或重算奖励来“恢复”。迁移采用兼容扩展，发布前确认旧版本在保留新增表/字段时仍能运行；如变更不兼容，另行准备明确恢复步骤并验证。
