# 步骤 5 · M2A 规则推荐、热门与反馈

更新日期：2026-10-30。状态：待实施。返回 [计划目录](README.md)。前置：[07 搜索与画像](07-m1c-search-and-profile.md)。下一步：[09 独立推搜前端](09-m2b-recommendation-ui.md)。

## 1. 目标与前置输入

在现有后端增加 RecommendationService，复用协会的共享搜索和数据读取，完成个人题单、换题、Hot、历史与反馈，供独立推搜前端调用。一期基线全流程不调用模型，不依赖任务创建或奖励服务。

输入为用户明确条件、按需画像、可靠题库、当前有效反馈和可配置规则。个性化推荐的范围始终受平台、主题、难度与数据覆盖限制。

## 2. 推荐请求与条件合并

请求包含 request_id、平台、允许主题/明确目标、各平台难度、总题数以及巩固/探索配额。默认总题数 5，允许 1～10，默认 3 道巩固与 2 道探索；该比例是试用起点，可调整或单独选择一种模式。

显式给出的两组数量应与总数一致，否则返回字段错误；只给总数时按配置确定性分配并回显。某组无合格题时说明不足，不能静默把探索配额改成巩固或突破主题。

条件优先级为当前表单要求 > 当前题单继承条件 > 可见且可编辑的默认值。不同平台使用各自难度范围，混合题单先分别筛选，再按明确配额编排。

推荐固定排除当前已知 AC；普通搜索可由用户选择是否排除。缺少画像时先依据用户选择的主题/难度或可编辑默认值推荐，不编造训练经历。

## 3. 巩固与探索策略

| 组别 | 候选方向 | 排序参考 | 约束 |
| --- | --- | --- | --- |
| 巩固 | 用户目标、近期练习或熟悉但久未练的题型 | 目标匹配、适宜难度、复习需求、近期曝光与热度 | 不把大量同类 AC 等同于已掌握 |
| 探索 | 用户选择的新方向；或少量教练维护的前置/相邻题型配置 | 前置条件适配、入门难度、低曝光和题单差异 | 低记录数只能说明已收集覆盖少 |
| 同题型难度挑战 | 用户明确希望提高熟悉题型难度 | 在允许范围内渐进 | 与探索新题型分开配置 |

初期前置/相邻题型用版本化小配置表达，无需知识图谱。没有可靠依据时让用户选方向或返回待补条件；不能仅看某标签为零就判定适合挑战高难题。

只允许 DP 的请求不会为了多样性返回图论题；缺少可靠 DP 细类时也不会生成“已核验数位 DP”标签。

排序先使用可解释的优先级：目标匹配 → 难度适配 → 组内复习/探索参考 → 曝光与反馈 → 热度 → 稳定题目 key。权重如有引入，记录版本并用试点评测调节，不把任意分数叫作能力模型。

## 4. 候选与最终题单

1. 读取当前有效绑定、Profile、条件、最近曝光和单题反馈。
2. 使用共享查询按组取候选，先执行硬过滤。
3. 排除已知 AC、可靠别名重复、已做过自报和不感兴趣等有效个人排除。
4. 按规则排序，减少高度重复的标签组合；同平台可在允许范围内难度递进。
5. 不足时继续查后续候选，直到满足、真实耗尽或执行预算用完。
6. 对最终候选重新核验当前已入库 AC、别名及有效性，必要时继续补题。
7. 保存不可变快照，返回实际条件、顺序、组别、真实依据和数据范围。

候选总量不等于第一页大小。预算耗尽、某组缺题、真实无匹配和数据不可核验分别返回原因；不能静默降低题数且声称全部满足。

理由由后端模板生成，例如“标签匹配二分、位于你选择的 CF 难度范围、作为巩固题”。展示历史数量时用“本系统已记录”，不输出未经证实的能力结论。

候选必须能够解析为已入库且可核验的 ProblemRef，但无需有本队 AC 历史。题库外题目的发现和补录不在推荐请求内临时完成，也不采用 LLM 直接生成的题号或 URL。

## 5. 快照、换题与请求幂等

recommendation_slate 保存 user_id、请求标识及摘要、父快照、条件、有序来源/规范题 key、依据、数据截止及规则版本；不要存入 task 表。本人历史读取返回当时结果，并可附当前有效性。

同一用户的同一 request_id 与相同内容返回原结果；不同内容报冲突。并发生成由数据库唯一约束与短事务保证，不只依赖查询后判断。

换题必须引用本人 slateId 和明确的题目 key；如果使用位置，同时验证位置与快照内容一致。候选排除原题及其他保留题的 canonical key，保存带 parent_id 的新快照。

保留题若已经 AC 或不满足更新后条件，返回整体刷新提示，不静默更换其他题。改变整份题单的平台、主题或难度时走完整重新生成流程。

## 6. 反馈与后续过题闭环

| 事件 | 默认作用 | 不产生的含义 |
| --- | --- | --- |
| exposure / click | 留存曝光与访问参考 | 不等于喜欢、完成或掌握 |
| too_hard / too_easy | 当前题及局部排序参考 | 不自动修改长期难度偏好 |
| not_interested | 本人对该题的排除，支持撤销 | 不默认屏蔽整个题型 |
| already_solved | 本人排除并提示核对，支持撤销 | 不直接写 AC、排名、热门或正式任务进度 |
| undo | 引用本人原反馈并取消其后续作用 | 不覆盖已存在真实 AC 和其他仍有效约束 |

recommendation_event 记录用户、题单、题目、事件标识、类型、值和撤销引用。校验题目属于对应快照、原反馈归属和撤销合法性；事件重试幂等。

新 AC 仍由 CF/洛谷原链路入库，下次查询生效。反馈和推荐服务不调用 TaskProgressService，不直接派发任务、发放猫猫币或经验。

## 7. Hot 统计

当前现役口径为 user.deleted=0 且 role_id=1，与某个 team_id 的成员范围不同。先在全部有效已知历史中按用户—规范题去重并取 first_observed_ac_at，再筛选近 7 天或 30 天，统计不同用户数。

使用统一 as_of，按人数、最近首次观测 AC 时间、稳定 key 排序。重复 AC 不增加人数，历史补传按原提交时间处理。别名或判题修正后下次查询或缓存刷新应反映新结果。

展示“按已收集记录统计”和来源时间，不能称为所有队员完整历史榜。Hot 以规范题跨来源汇总人数；平台筛选选择展示引用，人数仍是该规范题在已收集来源中的去重人数，页面说明这一口径。选定平台的题目引用必须真实存在，跨平台已核验同题不会重复增加同一人的贡献。

## 8. 可选模型候选如何接入

基础链路是“已入库 AC → 去重题型统计 → 标签/难度候选 → 规则编排”。只有 [14 E0](14-e0-cpu-model-evaluation.md) 证明收益后，才加入“题面/请求向量 → 相似候选 ID”这一支路，再统一做当前 AC、反馈、别名、主题和难度过滤。

语义相似只增加或排序候选，不能作为能力分数，也不能放宽用户条件。相似题缓存先产生候选，最终过滤后不足时按预算补充规则候选；仍不足则说明原因。基线不必为了这个选项先建设通用插件框架。

新 AC 默认只更新已做题和统计；已有题向量按文本版本复用。可选语义开关关闭或编码失败时继续使用规则推荐，单独记录候选来源、编码版本、耗时和降级原因。LLM 调用次数与 Embedding 调用次数分别统计。

ItemCF、ALS/BPR 和重排序均留作后续对照实验，不能将“下载预训练文本模型”描述成“已训练本队个性化模型”。曝光、点击、AC 与负反馈保留各自语义，为未来评测提供事实。

## 9. 交付与验收

交付推荐/热门/换题/历史/事件接口，快照与反馈迁移，规则配置、模板说明及关键校验。接口路径统一见 [02 架构设计](02-architecture.md)。

- [ ] 主题、平台、难度和数量契约执行一致，组配额不足有明确原因。
- [ ] 重复 AC、可靠别名、自报排除、撤销及新入库 AC 均正确处理。
- [ ] 候选不足继续分页；预算不足不被误报成题库耗尽。
- [ ] 换题不返回原题或保留题，保留题失效会提示整体刷新。
- [ ] 并发重试不产生多份题单或重复反馈；他人的题单、事件不可读写。
- [ ] Hot 按去重用户和全部已知历史最早 AC 计算，不按 AC 行或接收时间计算。
- [ ] 只有已核验字段进入说明，低数量未被描述为能力薄弱。
- [ ] 推荐、换题和反馈不会新增 task/task_assign 或产生奖励副作用。
- [ ] 一期基线服务独立于模型、会话和供应商配置；可选增强另行验收。
