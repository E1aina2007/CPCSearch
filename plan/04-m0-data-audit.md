# 步骤 1 · M0 数据审计与采集核验

更新日期：2026-10-30。状态：待实施。返回 [计划目录](README.md)。下一步：[05 采集接入](05-m1a-ingestion.md)。

## 1. 目标与范围

建立可用于开发的真实基线：表怎么存、记录从哪里来、有哪些缺口、哪些后端数据服务可以复用，以及独立前端如何接入现有登录。此步骤使用只读查询、受控快照和源码核对，输出问题清单，不批量修正正式排名、任务或奖励数据。

前置输入：当前源码、实际部署版本、可读数据库或快照、CF 采集器位置、洛谷脚本及接收端位置、少量试点队员的有效绑定。

当前仓库能找到 CF 脚本辅助入口，但这不能替代用户确认的“CF 官方 API、洛谷油猴上传”主链路。未找到的采集实现标为待接入核验，不据此改写实际来源。

## 2. 执行顺序

1. 核对实际 DDL、MySQL 版本、字符集、时间列类型、数据库与 JVM 时区、Flyway 现有迁移和已应用版本。
2. 核对 user.id、user_code、user_auth、oj_account 的关联；检查空绑定、一号多人、重复账号、改绑历史和两处绑定不一致。
3. 分平台统计提交行数、AC 行数、去重提交数、用户—来源题数量、记录起止时间；规范题口径待映射核验后补算。
4. 抽样检查提交标识、判题状态更新、题号、时间单位、重复上报、失败记录是否保存。
5. 分别记录 CF 分页/补齐/重判校正和洛谷监听范围/最终结果/上传确认/重试/历史补采行为。
6. 检查两张题库的实际 tags 格式、洛谷标签字典、难度缺失、孤立题号和可靠别名证据。
7. 固定试点用户与全部已收集历史范围，记录数据截止和样本选择理由。
8. 核对共享搜索、题目引用、权限与正式任务副作用；检查通用前端登录、HTTP 和 /main 下新增独立路由的方式，不将协会页面重构或任务预填列为交付前置。
9. 记录现有业务部署与资源限额。用户已给出的服务器快照见 [03](03-technology-options.md)；CPU 推理兼容性与性能仍是 [14 E0](14-e0-cpu-model-evaluation.md) 的待测事项，不在审计时顺带安装模型。

优先读取表定义、必要索引和指定样本，避免直接输出全表私人资料、认证数据或密钥。仓库的 full_schema.sql 没有完整覆盖 OJ 与协会表，不能替代线上 DDL。

## 3. 质量报告应包含什么

| 项目 | 记录内容 |
| --- | --- |
| 数据环境 | 版本、时区、快照边界、来源及查询范围 |
| 归属 | 有效绑定数、冲突数、影响用户和定位方式 |
| 重复与更新 | 来源键重复、相同题重复 AC、待判题转 AC 的处理情况 |
| 题号 | 未解析、缺题库、同题映射冲突及样例 |
| 标签 | 原始格式、可解析比例、规范词表匹配比例、未知细类 |
| 难度 | CF 与洛谷各自分布、未知比例、异常值 |
| 采集覆盖 | 每账号范围、最后成功时间、CF 历史是否补齐、洛谷是否只有监听 |
| 性能基线 | 记录规模、代表性查询耗时、执行计划与当前索引 |
| 复用范围 | 后端只读服务、通用鉴权/HTTP、独立前端接入点和共享代码回归范围 |
| 运行资源 | 用户提供的资源快照、实际应用/数据库部署、容器限额和未核验项 |

“最早一条记录的日期”不能直接写成完整历史覆盖起点。只有 AC 数据时，应明确不具备计算真实尝试次数、通过率和解题耗时的证据。

若准备研究推荐模型，可从已有统计顺带记录有效用户数、去重题目数、用户—题目交互数与分布，不要求为此新建画像或训练表。语义实验还需另查题面来源和覆盖；现有标题/标签不等于完整题面。模型数据准备不阻塞可靠试点的规则推搜开发。

## 4. 需要重点复核的源码线索

| 线索 | 对后续步骤的影响 |
| --- | --- |
| CFAllSubmission 使用 subId + account；协会 CfSubmissionDO 仅标 sub_id | 先查实际唯一约束，保留合法团队成员归属 |
| CFAllSubServiceImpl 跳过已存在记录 | 若实际采集复用该路径，需要补状态更新与并发幂等 |
| getPassInfo 的 DISTINCT 包含 AC 时间 | 同一道题不同时间的 AC 仍可能返回多行 |
| DataQueryServiceImpl 查询提交明细列表 | 增加聚合或必要字段查询，不能当现成去重画像 |
| 洛谷关键词查询存在 OR 组合 | 加括号后再与难度等条件组合 |
| CF URL 解析按数字/非数字拆分 | B1/B2 等索引需要结构化修正 |
| 旧搜索在 /api/admin/tasks 下 | 队员入口另设，复用 Service 而非放开管理路由 |
| TaskProgressService 关联奖励，创建主线任务可能自动派发 | 个人题单采用独立存储，不直接调用任务创建或结算 |

源码入口见 [架构证据](02-architecture.md)。实际缺陷范围以当前代码和采集调用关系复核为准，不把某条辅助写入路径的问题推定为所有线上采集都存在。

## 5. 交付物与完成条件

交付数据质量报告、匿名化异常样例及定位键、实际字段/键/索引清单、来源覆盖说明、修正优先级、试点名单与范围，以及后端复用、独立前端接入和回归清单。这些是实施时产物，本文件不代替实际报告。

- [ ] 试点用户的业务身份、OJ 归属可追溯；冲突已明确隔离。
- [ ] CF 和洛谷采集实现或外部接口契约已定位，未知行为有明确记录。
- [ ] 已确定重复记录与判题更新采用的来源身份和新鲜度证据。
- [ ] 标签、题号、难度和时间语义有代表性样例。
- [ ] 能说明哪些统计可计算、哪些因数据覆盖不足不能计算。
- [ ] 正式任务、奖励与排名的回归范围明确，没有用审计顺带修改其口径。
- [ ] 已区分服务器资源快照、实际部署限制与未执行的模型评测，没有把硬件信息当作推理验收。

若外部采集代码暂不可得，可先以已核验快照推进清洗和只读查询；采集可靠性仍标为未验收，不能据此宣称端到端同步完成。工期和索引方案在获得本步骤结果后确定。
