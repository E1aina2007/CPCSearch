# 步骤 2 · M1A 采集接入与幂等入库

更新日期：2026-10-30。状态：待实施。返回 [计划目录](README.md)。前置：[04 数据审计](04-m0-data-audit.md)。下一步：[06 规范化清洗](06-m1b-normalization.md)。

## 1. 目标与输入

沿用 CF 官方 API 和洛谷油猴上传，补齐可靠写入、更新、确认与覆盖状态。已有采集器满足要求时直接复用，不因重做推搜而另写一套爬虫或增加 MQ。

本步骤中的脚本只指已有洛谷采集链路；扩展到 CF 并在 AC 后展示推荐暂不进入实现范围。新增独立推搜前端消费同一个后端，不改变两平台的事实来源。

输入为 M0 的真实表键、账号归属、采集器位置、平台状态映射、时间格式及运行缺口。此步骤不把任意客户端上报升级为官方核验事实，也不改变正式排名的业务政策。

## 2. 统一接入契约

两类来源在各自适配器中转成内部提交 DTO，再执行账号范围、题号、时间和判题校验。业务表继续使用现有两张提交表，不强制复制一份完整事件库。

| 内容 | 处理要求 |
| --- | --- |
| 平台和来源 | 区分 CF 官方 API、洛谷脚本及其他已存在辅助来源，保留来源证据 |
| 提交身份 | 稳定 source_submission_id、来源账号；与实际 DDL 和团队提交语义一致 |
| 题目标识 | 来源 problem_id，CF 另保留可解析的 contestId/index；不能只按标题定位 |
| 判题结果 | CF 原 verdict；洛谷按已核验映射得到 is_pass；未知或中间态不作 AC |
| 时间 | 核对平台单位后转换；提交时间与服务端接收/核对时间分别表达 |
| 账号权限 | 由登录身份或受限采集身份确定允许上传范围，不信任任意 userId |
| 结果 | 区分 accepted、duplicate、updated、rejected；重复有效记录也能得到成功确认 |

旧表不具备来源与接收时间时，选择最小兼容字段或关联元数据扩展。保留源记录与必要纠错证据；“保留原始数据”不表示禁止更新已证实变化的判题状态。

## 3. CF：历史补齐、增量与校正

官方 user.status 根据 handle 返回提交，支持从 1 开始的 from 与 count 分页，并按提交 ID 降序返回；返回的是提交列表，业务层再识别 OK。[官方方法说明](https://codeforces.com/apiHelp/methods#user.status)

1. 从经核验绑定确定 handle，记录可访问范围和本轮历史补齐目标。
2. 分页获取并幂等写入，以稳定提交身份去重；不要把单次默认响应当成全部历史。
3. API 的分页偏移会受新提交影响。保存本轮已见边界，重叠读取并复核头部及分页衔接；最大提交 ID 不能单独证明中间无缺口。
4. 对成功落库范围推进检查点。部分分页失败时只标记部分完成，重试不能跳过失败区间。
5. 增量阶段从近期向后扫描至已覆盖范围并保留重叠；持续重新检查尚未终结状态。
6. 定期校正较早记录，处理重判或已知映射修正；不能只用创建时间查增量。
7. 按官方当前限制限速，失败采用退避，不能用重试风暴阻塞在线连接池。

Submission 的 verdict 可能缺失或处于评测状态，creationTimeSeconds 是提交创建时间。[官方对象说明](https://codeforces.com/apiHelp/objects#Submission)

同一提交由待判题更新为 OK 应生效，后来可信的非 AC 结果也必须允许纠正原 AC。没有可靠更新时间时，按来源核对结果与服务端采集顺序制定规则；不能采用 AC 永远优先，或仅凭客户端上传时间判定新鲜度。

当前 [CFAllSubServiceImpl](../be/src/main/java/gxuicpc/qingluan/service/impl/CFAllSubServiceImpl.java) 对已有键不更新。只有确认实际采集器调用此路径后才在对应边界改造；另有外部写入器时应统一其幂等与更新契约。

## 4. 洛谷：监听、上传、确认与补采

~~~mermaid
flowchart LR
    A["观察判题结果"] --> B["脚本持久保存待上传事件"]
    B --> C["携带允许的采集凭证上传"]
    C --> D["服务端校验归属、字段和来源"]
    D --> E["唯一约束下写入或更新"]
    E --> F["提交成功后确认"]
    F --> G["脚本移除已确认事件"]
    C --> H["失败或未确认"]
    H --> B
~~~

优先观察最终判题结果。如现有脚本也上传中间状态，必须使用同一提交标识关联后续变化。脚本应保存未确认事件，重载页面后恢复，按退避重传，并对无法重试的字段错误明确提示。

接收端区分两种授权：

- 本人脚本：由青鸾登录态确定用户，只允许其已绑定 UID 的记录。
- 已授权的集中采集：使用服务端认可的采集身份和账号范围，不能由普通个人凭证自行指定其他队员。

核验绑定能减少串号，不能证明客户端上报未被修改。保留来源和可信程度，沿用项目现有数据治理规则；不要仅为推搜新增采集所有洛谷数据的服务。

成功响应只在记录提交后发送；响应丢失后重传应返回已存在结果。稳定事件 ID/提交 ID 不能每次重试随机生成，来源判题变化使用同一提交的更新语义。

已观察但上传失败可通过重试恢复；没有被观察到的记录无法靠重试恢复。若脚本支持历史补采，明确其来源、范围和终止条件；不支持时标记 partial，提供“已做过”个人排除反馈。

脚本最后在线、最后收到事件与完整历史覆盖是不同概念。即使近期持续收到数据，也不能证明没有漏采。

## 5. 同步元数据与并发

优先复用能够按账号表达状态的现有存储，否则增加 oj_sync_state。记录 platform、account、user_id 或绑定引用、binding_version、coverage、history_backfill_state、cursor、last_successful_sync_at、last_event_received_at、error_status。

同一账号同一同步任务避免并发推进检查点；多实例需要数据库协调。记录写入与相应进度推进保持事务一致或有可验证的恢复协议，不能只依赖进程内变量。

并发幂等最终依靠实际唯一约束及数据库写入处理。迁移唯一键前先定位冲突；CF 团队提交可能关联多个成员，不能为满足 sub_id 唯一直接删除合法成员行。

一次重复请求返回 duplicate 不应重复产生过题通知、推荐反馈或其他派生业务。新 AC 的消费以已提交数据为准，本阶段无需新增消息队列。

入库与状态更新不调用 LLM 或 Embedding。未来若启用语义检索，题目向量按题目文本版本生成，可由所有用户复用，不按每条 AC 重复编码；向量任务失败不得影响提交入库确认。题目目录扩充也独立于提交采集，不要求一题先有人 AC 才入目录。

## 6. 交付与验收

交付采集接口契约、必要的采集器/接收端调整、兼容迁移、同步状态说明和端到端演练记录。代码落点以实际采集实现为准；现有 [HttpTaskExecutor](../be/src/main/java/gxuicpc/qingluan/schedule/core/HttpTaskExecutor.java) 只是外部 HTTP 调用执行器，不证明已有完整同步能力。

- [ ] 同一提交重复上传和并发重试不增加来源记录或去重过题数。
- [ ] 待判题 → AC、可信 AC → 非 AC 更新均可追溯且生效。
- [ ] CF 分页中断可恢复，新增提交引发偏移时不会被误标为补齐完成。
- [ ] 写入失败不推进检查点；响应丢失后的重传不会产生重复副作用。
- [ ] 洛谷脚本重载后能恢复已保存但未确认的事件。
- [ ] 本人凭证不能提交他人的记录；集中采集身份范围经过校验。
- [ ] 时间转换、提交身份与真实样本一致。
- [ ] 缺失历史、最后同步和来源可信度可被推荐侧读取。
- [ ] 模型未配置、Agent 关闭或可选语义任务失败时，原提交采集与确认链路仍可运行。

外部脚本或采集器无法演练时，明确该段尚未验收。可继续对可信已入库快照开发，但 M3 不能把未演练的采集闭环列为通过。
