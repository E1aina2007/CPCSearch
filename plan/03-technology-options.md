# 技术选型、服务器约束与备选方案

更新日期：2026-10-30。状态：选型建议，未安装推理运行库、下载模型或接入供应商。返回 [计划目录](README.md)。

## 1. 当前采用的组合

一期基线：Java 17 + 现有 Spring Boot 3.5.6 + MyBatis/MyBatis-Plus + MySQL，使用 Java/SQL 完成规范化、条件搜索、题型统计、规则推荐和模板说明。后台工作优先复用 Spring 调度，迁移沿用 Flyway。

前端：Vue 3 + Element Plus + Axios，默认在 newfe 中新建 features/recommendations 与独立路由，复用通用登录、请求和组件。不复用冒险家协会页面、布局或任务表单；暂不新增前端工程和部署单元。

二期 Agent：同一后端内增加 AssistantService，以现有 HttpClient5 + Jackson 调用一个供应商 LLM API。会话、偏好、题单与请求状态使用 MySQL；先不引入 Agent 框架、向量记忆或通用工作流引擎。

可选增强：在独立实验中比较小型预训练 Embedding 的 CPU 推理与供应商 Embedding API。效果、兼容性和资源占用通过后，才增加语义候选入口；它不是一期或 Agent 的前置依赖。

依赖已核对 [be/pom.xml](../be/pom.xml) 与 [newfe/package.json](../newfe/package.json)。前端仍是 Vue CLI 工程，已有 Redis 可按测量结果复用。CPCSearch 不是本方案必需落点，Go/Python 常驻服务、MQ 和搜索集群均不进入基线。

## 2. 为什么第一版不用向量库或推荐模型

目前核心输入是平台、题号、标签、难度和已入库 AC。SQL 可以筛选候选，Java 可以根据去重题型统计、明确目标和近期反馈编排题单。数据覆盖、标签可靠性和身份归属是首要问题，模型不能替代这些工作。

向量库解决向量的存储与相似检索，不自动生成向量，也不直接产生适合个人的训练题单。小语料的语义实验可以先在 Java 内存计算相似度或预计算相似题，是否增加专用索引取决于实测规模与并发。

第一版采用可解释规则还能形成效果基线，积累曝光、点击、换题和反馈，供后续模型公平比较。只有 AC 的历史也可以作为隐式正反馈研究，但未 AC 不等于不喜欢或能力不足，不能直接作为可靠负样本。

## 3. 服务器资源与推理边界

| 项目 | 已提供信息 | 对方案的影响 |
| --- | --- | --- |
| 系统 | Debian 13，Linux 6.12.63+deb13-amd64，x86_64 | 选择 Linux x64 CPU 运行库，仍需实机验证 |
| CPU | Xeon E7-8850 v2 @ 2.30GHz，VMware，可用 CPU 数 16 | 视为 16 个可见 vCPU，不承诺专用物理核心或空闲容量 |
| 指令集 | 输出显示 AVX、F16C，未显示 AVX2/AVX-512 | 不直接使用要求更高指令集的二进制或优化配置 |
| 内存 | 总量 62.89 GiB，可用 32.91 GiB | 有开展小模型试验的容量空间，不能全部分配给模型 |
| Swap | 总量 0.95 GiB，空闲 0 | 需结合持续换入/换出判断，不能单凭已满认定正在内存不足 |
| 负载 | 1/5/15 分钟为 5.47 / 5.81 / 5.90 | 不是 CPU 使用率，也不证明还剩多少可用核心 |
| 根分区 | 总量 27.3 GiB，可用 6.0 GiB | 下载前核对数据盘、缓存目录和容量，不默认其他磁盘也仅剩这些空间 |
| GPU | 用户说明无可用于推理的 GPU | 基线与供应商 LLM 路径不受影响，CPU 模型另做评测 |

工程判断：可以评估小型 CPU Embedding 和传统推荐算法；尚不能承诺某模型可用或在线时延达标。先检查兼容性与低并发性能，不把网上 AVX2/AVX-512 机器的测速套到本机。Linux 负载还包含部分 I/O 等待任务；持续换页可通过 vmstat 的采样观察。[loadavg 文档](https://man7.org/linux/man-pages/man5/proc_loadavg.5.html)、[vmstat 文档](https://man7.org/linux/man-pages/man8/vmstat.8.html)

本机部署对话大模型不进入当前路线，Agent 使用供应商 API。“无 GPU”不再被表述为“完全不能部署任何模型”。

## 4. 可替代技术栈对照

备选均需评测，不是本期安装清单。优先选择能解决实际缺口、增加最少部署和维护工作的方案。

| 层次 | 基线选择 | 备选 | 增加的成本或限制 | 引入条件 |
| --- | --- | --- | --- | --- |
| 后端组织 | 现有 Java 应用与共享只读 Service | 提取独立 Java 服务 | 部署、鉴权传递、跨服务契约 | 出现独立扩缩容或团队边界需求 |
| 前端组织 | newfe 内独立推荐模块与路由 | 独立 Vue 工程 | 重复鉴权接入、构建、发布与路由维护 | 确有独立站点/发布需求 |
| 结构化搜索 | MySQL 条件查询、题号、规范标签 | FULLTEXT/ngram | 正文、索引、分词配置与评测 | 明确需要正文关键词检索 |
| 大规模全文搜索 | 先使用 MySQL | OpenSearch/BM25 | 新服务、索引同步与重建 | 检索效果和规模实测超出当前方案 |
| 语义编码 | 基线关闭 | 预训练小模型 + ONNX Runtime Java CPU | 模型与分词资产、JNI 兼容、线程和内存 | E0 在本机验证有效且可承受 |
| 语义编码替代 | 同一接口下选择一种实现 | 供应商 Embedding API | 网络、费用、文本发送与版本变化 | 本地不适配或维护成本更高 |
| 向量检索 | 小语料 Java 内存精确计算或相似题预计算 | Qdrant 等专用向量服务 | 新存储、备份、同步、权限和运维 | 扫描/更新/并发实测成为瓶颈 |
| 题型画像 | 按用户 SQL 聚合与字段投影 | user_problem_progress 汇总表 | 回填、重判和改绑修正、缓存一致性 | 查询优化后仍未达性能目标 |
| 推荐排序 | Java 规则、标签与难度编排 | ItemCF 共现、ALS/BPR、学习排序 | 交互处理、离线评测、训练或重算 | 用户与题目交互足以支撑并有可验证收益 |
| 语义重排序 | 基线关闭 | 预训练 Reranker 的 CPU/API 推理 | 逐对评分成本与额外延迟 | 有限候选上的质量提升值得付出成本 |
| 清洗与调度 | Spring 调度、检查点、数据库协调 | 独立调度平台 | 控制面、权限和任务治理 | 跨应用依赖已成为实际问题 |
| LLM 客户端 | HttpClient5 + Jackson | Spring AI | 依赖、协议抽象和版本兼容 | 多供应商维护成本确实上升 |
| LLM 供应商 | Qwen 工具调用 API 为初始候选 | DeepSeek 等供应商 API | 协议、模型能力、额度和费用需复测 | 固定业务样本显示更合适 |
| 记忆 | MySQL 类型化偏好、会话与结果引用 | 用户隔离的语义索引 | 文本编码、删除同步与权限过滤 | 大量复盘文本确实需要语义查找 |
| 缓存 | 请求内复用；需要时复用 Redis | 短期进程缓存 | 多实例一致性、陈旧结果管理 | 仅用于可重建且允许短期陈旧的数据 |
| 前端响应 | 普通 HTTP | 二期流式响应 | 断连恢复、代理与取消语义 | 体验实测需要逐步输出 |

MySQL ngram 支持 CJK 全文解析，具体版本与索引需核对；OpenSearch 提供 BM25 等全文能力，Qdrant 提供向量检索。这些服务都不能替代业务过滤。[MySQL](https://dev.mysql.com/doc/refman/8.0/en/fulltext-search-ngram.html)、[OpenSearch](https://docs.opensearch.org/latest/search-plugins/keyword-search/)、[Qdrant](https://qdrant.tech/documentation/overview/)

若考虑 Spring AI，需核对所选版本与 Java 17 / Boot 3.5.6 的兼容，不为接模型顺带升级整个项目。[Spring AI](https://docs.spring.io/spring-ai/reference/)

## 5. 哪些模型需要训练

| 方案 | 是否需要本队训练数据 | 运行方式与限制 |
| --- | --- | --- |
| 标签/难度规则 | 不需要模型训练 | Java/SQL，可直接开发 |
| ItemCF 共现相似度 | 需要清洗后的用户—题目交互来统计 | 可在 CPU 重算，不必引入神经网络 |
| 预训练 Embedding | 首轮通常不需要微调 | 用题目文本直接评估；不等于个性化推荐模型 |
| 预训练 Reranker | 首轮可直接评估 | CPU 或供应商 API，需测候选数量和时延 |
| ALS/BPR 或学习排序 | 通常需要拟合本队数据与目标 | CPU 可承担部分传统方法；其他项目的用户/题目 ID 权重不能直接套用 |
| Agent LLM | 本期不训练 | 供应商 API + 工具边界 + 结构化记忆 |
| 生成式召回 | 取决于题目标识、模型与任务适配，通常需专门训练/微调和评测 | 独立研究，不是推荐题单或 Agent 必需环节 |

Implicit 项目提供 ALS、BPR 等算法的多线程 CPU 训练实现，说明传统推荐训练并不必然要求 GPU。这里只作为可行性参考，不把其 Python 运行环境加入生产服务。[官方项目](https://github.com/benfred/implicit)

CPU Embedding 首轮候选为 multilingual-e5-small（中英文混合题库）与 bge-small-zh-v1.5（中文较小模型基线）。模型规格、编码要求、长题面处理和对照实验统一见 [14 E0](14-e0-cpu-model-evaluation.md)，不将模型榜单表现当作本项目效果。

## 6. 供应商、RAG 和记忆

A0 只接一个支持工具调用的供应商，先评估 Qwen，再按相同样本比较 DeepSeek 等备选。固定实际模型 ID、地域、协议、上下文预算和额度；不预设某个型号必然最好，也不建立多模型网关。[Qwen 工具调用](https://help.aliyun.com/zh/model-studio/qwen-function-calling)、[DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)

Agent 常见请求一次模型调用解析动作，Java 工具执行后可直接返回卡片和模板，不固定追加润色调用。API Key 仅在后端配置，关闭 Agent 不影响一期基线。

基于事实的回答可以通过 SQL/业务工具取回题目和训练概况，RAG 不等于必须使用向量数据库。会话状态与明确偏好以 MySQL 为权威；题目向量是检索索引，不是记忆。只有复盘文本达到需要语义检索的规模，才另评估带用户隔离和删除同步的记忆索引。

## 7. 题面数据与更换技术的顺序

现有题库实体提供题号、标题、难度和标签，没有完整题面字段。一期不要求补齐题面。若进行 E0，可选约 1,000～2,000 道可靠样本补正文，并评估 [open-r1/codeforces](https://huggingface.co/datasets/open-r1/codeforces) 等来源的版本、字段、许可与题号覆盖；数据集不替代本队提交记录。

题面、题解与算法标签分别标识，不把题解作为默认展示内容。题目故事相似未必意味着算法相似，语义效果必须以真实训练目标评价。

执行顺序为：审计并清洗可靠试点 → 完成规则推搜基线 → 按缺口选择 E0 或二期 Agent。E0 的小实验可在有文本样本后提前进行，但不阻塞主线；在收益明确前不增加向量服务、训练流水线或额外常驻进程。
