# 可选步骤 · E0 CPU 模型评测与语义检索

更新日期：2026-10-30。状态：可选实验，尚未执行兼容性、效果或性能测试。返回 [计划目录](README.md)。资源快照与选型依据见 [03](03-technology-options.md)。

## 1. 目标、前置与退出方式

验证小型预训练 Embedding 能否在当前服务器上改善中英文题目检索，并判断 CPU 本地运行、供应商 Embedding API 或继续使用规则推荐哪一种更合适。本实验不训练对话大模型，不把服务器可用内存当作上线依据。

前置是 M1B 已有可靠题号、标签和少量合规文本。试验可以提前开展；正式接入需有一期规则基线、可解释收益和本步骤验收。实验失败、收益不足或暂缓，都不阻塞 M3 交付或 A0～A2 的供应商 Agent。

先做单模型、小样本、低并发试验，不同时安装多个推理框架，不在正式 Java 进程中第一次验证原生库兼容。浏览器脚本的 CF 扩展与推荐注入不属于本步骤。

## 2. 首轮候选与需要训练的边界

| 候选 | 已知特点 | 在本项目中的实验用途 |
| --- | --- | --- |
| multilingual-e5-small | 预训练多语言 Embedding，384 维，最多 512 tokens | 优先验证 CF 英文、洛谷中文及跨语言查询 |
| bge-small-zh-v1.5 | 约 24M 参数的中文 Embedding | 中文小模型基线，不能默认代表英文题效果 |
| 供应商 Embedding API | 由供应商推理，能力、维度与版本按实际接口核验 | 本地兼容或维护成本不合适时的对照方案 |

模型规格来自作者模型卡：[multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small)、[bge-small-zh-v1.5](https://huggingface.co/BAAI/bge-small-zh-v1.5)。首轮可以直接评估预训练权重，不要求先微调。不同模型、编码约定的向量不直接放入一个相似度空间；也不把两个单语模型的向量拼在一起冒充跨语言检索。

Embedding 的目标是找到相关文本，不能直接证明题型相同、难度合适或用户掌握程度。Reranker 留到召回基线有效后再评估，先限制候选数量；ALS/BPR 等个性化方法需另用本队交互拟合，生成式召回仍为独立研究。

## 3. CPU 运行方式与兼容性

生产候选为同一 Java 后端中的可选 EmbeddingService，采用 ONNX Runtime Java CPU 或供应商 API 的一种实现。官方提供 JVM 接口和 Linux x64 CPU 包，但平台支持列表不证明某个具体原生库在当前老款 Xeon 上一定可运行。[ONNX Runtime Java 文档](https://onnxruntime.ai/docs/get-started/with-java.html)

依次执行：

1. 复查 CPU 指令、实际进程/容器资源限制、可用数据盘、缓存路径及现有业务负载。当前仅看到 AVX/F16C，未显示 AVX2；不修改系统 Swap、清理业务缓存或占满全部 CPU。
2. 固定模型 revision、权重与分词资产校验值、来源许可、ONNX 导出配置及运行库版本。优先使用可验证来源的产物；需要导出时可在开发环境完成，不要求生产常驻 Python 服务。
3. 在独立进程中验证兼容的 CPU/FP32 基线：加载、分词、推理、输出维度、数值有效性和重复运行。FP32 只是首轮基线，不保证所选二进制兼容。
4. 对照官方参考实现，检查 token IDs、attention mask、截断、池化和归一化；必要时比较浮点误差与固定样本排序。仅加载 safetensors/ONNX 文件不等于已经完成可用的 Embedding 接入。
5. 先用 1～2 个推理线程和低并发测量，再根据数据调整。兼容性不通过时记录具体运行库/算子错误，优先比较 API 路线，不把长期维护自编译运行库变成默认要求。
6. 基线稳定后才评估 INT8 等量化；在同一数据上同时比较质量、延迟与内存。不能默认旧 CPU 的 INT8 必然更快。

Sentence Transformers 文档列出的量化配置包含 avx2、avx512 等特定目标，不能直接当成本机可用配置或性能结论。[官方优化文档](https://sbert.net/docs/sentence_transformer/usage/efficiency.html)

原生库非法指令或崩溃可能终止 JVM；只有独立试验通过才考虑嵌入业务进程。即使通过，仍需限制线程、队列、批量和请求超时；如果隔离成本超过收益，继续使用 API 或关闭该增强。

## 4. 文本与向量版本

现有两张题库实体没有完整题面。先抽取约 50～100 道可靠中英文题目做兼容性和初步质量检查，通过后再扩大到约 1,000～2,000 道；样本规模是试验起点，不是已有数据量。

保留题意、输入输出和关键约束，分离题解。长文本采用显式、版本化的截取或分块方案，记录被截断比例；不能默默裁掉决定算法的条件后声称完整题意已经编码。仅标题/标签样本单独评测，避免用标签输入再次匹配标签造成虚假的语义提升。

E5 的查询/文档检索按模型要求使用 query:/passage: 前缀，含中文输入；参考实现使用掩码平均池化与归一化。题对题相似需要固定并评测自己的对称编码约定，不把带不同角色前缀的向量随意互换。[E5 用法](https://huggingface.co/intfloat/multilingual-e5-small)

每个 embedding_profile_id 固定模型 revision、分词器、输入角色/前缀、文本处理版本、池化、归一化与维度。题目向量同时记录 source_problem_key、content_hash 和生成状态；由 profile 判定兼容的比较空间，不能仅凭维度相同就混算。

MySQL 中的题目、已核验别名和过题事实仍为权威；向量是可重建派生数据。文本、标签或编码输入发生变化时，只重建受影响版本；新版本回填完成并通过检查后再切换，支持回到上一有效版本或关闭语义支路。

从本地模型换成另一供应商的 Embedding 时也按新空间重建语料向量；不能只替换查询端点，继续与旧题目向量比较。查询编码和题目索引必须匹配同一已验证的编码契约。

## 5. 与推荐链路的连接

~~~mermaid
flowchart TD
    T["已核验题目文本"] --> B["后台批量编码"]
    B --> V["版本化向量 / 相似题缓存"]
    Q["新语义查询"] --> E["CPU 或 API 查询编码"]
    E --> S["相似候选检索"]
    V --> S
    P["已有题作为种子"] --> V
    S --> F["目录有效性、AC、反馈、平台、标签和难度过滤"]
    R["一期规则候选"] --> F
    F --> O["规则编排、最终复查、个人题单"]
~~~

小题库先用 Java 内存精确相似度计算，或者离线保存种子的相似题 ID。向量文件、数据库扩展或缓存的具体形式按加载与更新需求选一种，优先保持现有 MySQL 和应用进程，不先建设向量服务。

以已有题为种子可复用向量或预计算结果，不要求用户每次 AC 都重新编码。新自然语言查询需要编码；无法编码时明确降级到结构化输入，不把关键词结果伪装成语义结果。此处是后端候选能力，不包含油猴页面推荐展示。

候选必须来自已入库且可核验的目录。当前已做题、别名、反馈和难度需在读取缓存后重新过滤；预计算 Top-K 不足时，在预算内扩大候选或补充规则结果，仍不足则如实说明。题库中没有向量的题仍可由规则路径推荐。

语义开关独立于 Agent 开关。题目向量不作为会话记忆，Agent 继续使用 SQL/业务工具与 MySQL 偏好。可选模型依赖的初始化应受开关控制，两者关闭时普通后端无需模型文件、运行库或 Key 即可启动。

## 6. 质量、性能与成本评测

在查看实验结果前固定样本、判分标准和可接受资源预算。使用同一题目目录和硬约束比较规则基线、规则＋语义候选；供应商 API 若参与，单独记录模型、版本、费用和发送文本范围。

| 维度 | 记录内容 |
| --- | --- |
| 检索效果 | 中英文、跨语言、同算法不同背景、同背景不同算法、长题面；人工标注的 Top-K 相关性与漏召回 |
| 训练价值 | 队员/教练对题型、难度、巩固与探索适配的评价；不以语义分数代替 |
| 硬约束 | 已知 AC、别名、反馈、平台、主题、难度、目录有效性违规，验收样本目标为 0 |
| 推理性能 | 冷启动、预热后单查询 P50/P95、1/2 并发、短文本与接近上限文本、失败率 |
| 完整链路 | 编码、候选检索、SQL 过滤、规则编排各段与总延迟，不能只报告裸模型耗时 |
| 批量与资源 | 编码吞吐、RSS/原生内存、CPU、队列、持续换页、磁盘与缓存占用 |
| 共享业务 | 模型关闭与开启时原采集、排名、SQL 请求的变化，离线任务是否影响在线 |
| API 对照 | 超时、重试、额度、输入规模与实际费用，未知用量明确标记 |

先测单请求和少量并发，再决定是否增加压力，不能把 16 vCPU 当作 16 个独占推理线程。Swap 满不等于正在换页，负载均值不等于 CPU 利用率；指标解释按 [03](03-technology-options.md) 的边界执行。

E0 不预设每秒请求数或毫秒级响应承诺。接受标准在试验前结合已有业务预算制定；效果没有稳定提升、延迟不合适、老 CPU 兼容维护复杂或影响原业务，都可以得出“暂不启用”的有效结论。

## 7. 交付、接入与回退

交付固定的模型/编码版本说明、样本与评测方法、兼容性记录、质量/资源/费用报告，以及采用 CPU、API 或保持关闭的决策。先完成报告，决定采用后再实现正式 EmbeddingService、派生存储和开关，不把实验写成已上线功能。

- [ ] 本机指定版本运行库与模型已实测，不以官方平台列表替代兼容验收。
- [ ] 分词、前后处理、向量空间、长题面处理与版本一致性可复核。
- [ ] 相同输入与硬约束下对比过规则基线，效果不是只由背景词或输入标签造成。
- [ ] 记录单请求、低并发、批量编码和旧业务影响，未测项没有填为通过。
- [ ] 接入时仍排除当前已知 AC，缓存不足、索引缺失和错误均有明确处理。
- [ ] Agent 与语义增强的开关、配置、调用和费用统计独立。
- [ ] 关闭语义增强后无需权重或运行库，规则搜索、推荐、采集与供应商 Agent 可按各自配置运行。
- [ ] 模型版本切换与回退不改变原始提交、明确偏好、历史题单和正式任务数据。

部署时先在语义关闭状态发布兼容代码，低峰回填样本并检查资源，再向试点开放。故障时关闭语义入口/候选支路，保留可追溯的模型与索引版本，继续使用一期规则服务；不删除业务数据来回退实验。
