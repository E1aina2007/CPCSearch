# 步骤 4 · M1C 共享搜索与按需题型统计

更新日期：2026-10-30。状态：待实施。返回 [计划目录](README.md)。前置：[06 规范化清洗](06-m1b-normalization.md)。下一步：[08 规则推荐](08-m2a-recommendation.md)。

## 1. 目标和输入

实现无模型的条件搜索与按需题型画像，直接使用已入库记录，不先建设画像服务或过题汇总表。输入为可靠账号绑定、来源记录、题库、规范标签、别名及覆盖状态。

共享契约见 [02 架构设计](02-architecture.md)。本步骤输出可被普通接口、推荐服务和后续 Agent 共同调用的 Java 方法。

## 2. 搜索执行顺序

1. 从登录态解析 user.id 和有效绑定；校验参数类型、分页上限及平台枚举。
2. 对明确题号做精确解析；对算法同义词查版本化词表，不使用模型猜测任意自然语言。
3. 将题号/标题关键词的 OR 放在同一括号内，再与平台、标签、难度、有效性组合。
4. 标签按规范关系精确匹配，多标签默认全部匹配；如开放任一匹配，用明确 tagMatch 参数并回显。
5. excludeSolved=true 时，基于全部已知历史的去重 AC 集合排除题目及已核验别名。
6. 按确定排序加稳定源题 key 打破并列，返回分页、实际条件、数据范围及有效 ProblemRef。

默认分页 20，最大 100，与现有搜索常量保持兼容。CF rating 与洛谷等级使用独立参数；严格难度条件下排除 unknown，未知细类返回字段提示，不能混入宽泛标签结果。

SQL 使用参数绑定与固定列/排序白名单。SQL 条件和值不能由用户或后续模型直接拼成完整语句。

当前 [SearchServiceImpl](../be/src/main/java/gxuicpc/qingluan/modules/Adventurers/Service/data/SearchServiceImpl.java) 已有平台查询和分页基础，需补标签、已做题排除及稳定组合。旧管理端搜索签名保留适配，队员通过新的 /api/adventurers/problems/search 调用共享方法。

该后端路径不意味着复用协会前端；新页面从 features/recommendations 发起请求。基础搜索只保证题号、标题关键词与规范标签条件，不把任意中文描述理解或题面语义相似作为本步骤承诺。

## 3. 按请求计算题型画像

建议逻辑管线：

~~~text
当前业务用户
  → 经核验的账号归属和绑定版本
  → 这些账号全部已收集的有效 AC（必要字段）
  → 来源题号关联可靠别名，缺省以自身作为规范题
  → 按 canonical_problem_key 去重并计算最早/末次提交时间
  → 关联题目规范标签与平台难度
  → 按标签聚合题数、近期新增、最近练习和难度分布
  → 附加来源覆盖与标签匹配比例
~~~

源记录缺题库元数据但题号有效时，仍进入已知 AC 排除集合；其标签统计留空并降低标签覆盖比例，不能因为缺标签就把已做题再次推荐出来。

| 字段 | 计算口径 | 使用方式 |
| --- | --- | --- |
| solvedProblemKeys | 全部已知有效历史中的规范题集合 | 推荐排除；不能只取最近 30 天 |
| solvedCountByTag | 每标签 COUNT DISTINCT 规范题 | 练习覆盖参考 |
| recentNewSolvedByTag | 先按全部已知历史求最早 AC 提交时间，再过滤窗口 | 近期新增，而非窗口内 AC 行数 |
| lastPracticedAtByTag | 本标签有效 AC 提交时间最大值 | 最近练习参考 |
| difficultyByPlatformAndTag | 按平台统计有效已做来源题的难度分布，注明样本数 | 可编辑难度参考，不跨平台求平均 |
| metadataCoverage | 有规范标签的有效已做题 / 全部有效已做题 | 无样本返回空状态，不能当历史完整率 |
| sourceCoverage | 每个来源的范围、同步和补齐状态 | 控制文案和默认推荐强度 |

同题多个标签可各计一次，所以各标签数量相加可能大于总过题数。经核验的跨平台同题在整体题数中计一次；各平台难度统计保留其来源，并显式说明该口径，避免合并难度单位。

没有可靠完整尝试数据时不输出成功率、WA 次数、解决耗时或“掌握百分比”。少量样本或洛谷覆盖不足时，采用用户明确条件、可编辑默认值或教练选题，不据此断言薄弱题型。

## 4. 查询实现与性能边界

复用 [DataQueryServiceImpl](../be/src/main/java/gxuicpc/qingluan/modules/Adventurers/Service/data/DataQueryServiceImpl.java) 的账号访问关系及 Mapper。当前方法返回明细列表，推荐侧应新增 SQL 聚合或必要字段投影，避免直接把原方法当成完整画像实现。

按用户过滤后再进行去重和标签聚合。来源键与标签/别名表可索引关联，字段仅包含该统计所需内容。禁止全队原始记录加载到 Java 后再筛一名用户，也不对每道题逐个查询标签。

索引候选围绕账号、判题、题号/时间及标签关联键，根据实际 DDL、选择性、EXPLAIN 和执行耗时确定。本文不固定适用于所有数据规模的索引列顺序。

初期直接查询 MySQL，并在单次推荐请求内复用同一统计结果。索引和投影优化后仍不达标，才评估 user_problem_progress 汇总表或缓存；引入时补全重判、改绑、别名变更的失效机制。

读取时固定必要规则/映射版本与截止时间，来源 last_successful_sync_at 独立返回。推荐返回前仍要用新查询复核最终候选的当前已知 AC。

## 5. 与未来语义检索的接口边界

结构化搜索使用完整的有效目录，不限于有 AC 的题目或未来有向量的题目。E0 若通过，可补充候选 ID 来源，但已做题、有效性、平台、难度和标签约束仍调用同一业务过滤逻辑，不能建立另一套“模型可信即通过”的查询。

新自然语言语义查询需要生成查询向量，已有题作为种子可复用其索引；缺向量、模型超时或索引版本不一致时返回明确状态，保留本步骤的零模型搜索。语义相似分数不写入 Profile 的掌握程度或过题事实。

## 6. 交付物与验收

交付共享搜索 DTO/Service/Mapper、Profile DTO 与聚合方法、兼容旧入口的适配、查询计划记录和关键业务检查。

- [ ] 精确题号、CF B1/B2、洛谷 pid、标题及规范算法同义词返回正确结果。
- [ ] OR 不能绕过难度；多标签语义、未知难度及未知标签行为明确。
- [ ] 超过近期窗口的历史 AC、重复 AC、已核验镜像题均正确处理。
- [ ] 缺题库元数据的有效 AC 仍参与已做题排除。
- [ ] 新增过题先在全部已知历史上取最早提交时间；历史补传不被当作今日新增。
- [ ] 多标签统计、无样本、部分覆盖与难度单位可解释。
- [ ] 查询没有逐题 N+1，也没有先加载全队全部明细再过滤。
- [ ] 数据归属冲突时不假装完成可靠个性化过滤。
- [ ] 旧管理端搜索及原有调用方仍符合既有契约。
- [ ] 本步骤基线模型调用数为 0，未依赖聚合表、会话表、模型运行库或向量库。

验证样例要覆盖真实业务边界，不为简单字段访问和低风险展示逻辑堆叠重复测试。性能目标由步骤 10 在完整试点规模下验收。
